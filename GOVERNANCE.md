# Governance

rappidAI Research is currently a small, maintainer-led project. This document
describes the process that exists today; it does not imply a foundation,
steering committee, or larger team.

## Maintainer responsibility

The repository is currently maintained by
[@jonascikemgil07-hue](https://github.com/jonascikemgil07-hue). The maintainer
sets repository scope, reviews contributions, manages releases and community
spaces, and makes the final merge decision.

Maintainer authority is also a responsibility to:

- apply the Code of Conduct consistently;
- distinguish verified facts from plans and self-reported results;
- review security, privacy, accessibility, and licensing impact;
- preserve contributor attribution and third-party notices; and
- explain significant decisions when doing so is safe and practical.

## How decisions are made

Routine fixes are discussed and reviewed in their issue or pull request. Larger
changes should begin with a public issue describing the problem, alternatives,
trade-offs, compatibility impact, and evidence. Examples include changing the
site architecture, public model naming, licensing scope, data claims, or the
release process.

The maintainer seeks rough consensus where practical, but consensus is not a
vote and does not guarantee acceptance. The maintainer may decline a change
that lacks evidence, creates unsustainable maintenance work, conflicts with the
project's scope, or introduces unresolved legal or safety risk.

Security incidents, conduct reports, personal information, and other sensitive
matters are handled privately rather than through public consensus.

## Pull requests

A pull request may be merged when it is in scope, reviewable, appropriately
tested, documented, and free of known provenance or licensing problems.
Passing automated checks is necessary when checks exist, but is not by itself
approval. The maintainer may request changes or close a proposal with an
explanation.

Contributors do not merge their own change unless they are the only available
maintainer and have completed the same review expected of an external change.
Material conflicts of interest should be disclosed; an independent reviewer
should be sought when one is realistically available.

## Disagreements and appeals

Technical disagreement should stay focused on evidence, trade-offs, and project
goals. First try to resolve it in the relevant issue or pull request. If the
discussion stalls, summarize the viable options and ask the maintainer for a
decision.

Conduct enforcement follows [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Security
reports follow [SECURITY.md](SECURITY.md). These private processes should not be
relitigated in public issues.

## Becoming a maintainer

There is no automatic path or fixed contribution count. A contributor may be
invited to maintain the project after sustained, constructive participation
that demonstrates sound judgment, reliable review, respect for project scope,
and care with security and licensing. Access should begin with the least
privilege needed and can be removed if it is unused or misused.

If the maintainer becomes unavailable, a successor should be chosen from active
trusted contributors where possible, with the transition documented publicly.

## Changing this governance

Governance changes use the same public pull-request process as other major
changes. This file is expected to evolve if the contributor base and project
responsibilities grow.
